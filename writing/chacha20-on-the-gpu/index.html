ChaCha20 on an OpenGL compute shader

31 Oct 2026

ChaCha20 suits a GPU. Its keystream is a sequence of independent 64-byte blocks, each a pure function of the key, nonce and block counter, built from 32-bit add, rotate and XOR. Any thread can compute any block without talking to another thread. This note walks through how the ChaCha20 GPU Image Encryption project maps that onto an OpenGL compute shader. It also covers three problems that turned up when re-reading the code: one is cosmetic, one concerns performance, and one concerns correctness.

The state and the quarter-round

The block function works on 16 words: four constants ("expand 32-byte k"), eight key words, a 32-bit block counter and three nonce words. That is the RFC 8439 layout. In GLSL the state is a uvec4[4], and the quarter-round is four add-XOR-rotate lines:

uint rotl(uint x, int n) { return (x << n) | (x >> (32 - n)); }
void QR(inout uint a, inout uint b, inout uint c, inout uint d) {
    a += b; d ^= a; d = rotl(d, 16);
    c += d; b ^= c; b = rotl(b, 12);
    a += b; d ^= a; d = rotl(d, 8);
    c += d; b ^= c; b = rotl(b, 7);
}

Ten double rounds (four column quarter-rounds, then four diagonal ones) and the final addition of the input state give one keystream block. GLSL's uint arithmetic wraps modulo 232, which is what the cipher needs.

Mapping blocks to invocations

The plaintext is a batch of decoded images packed into one SSBO (buffer { uint data[]; }), padded to a multiple of 128 bytes. Each invocation produces two consecutive blocks:

uint id = gl_GlobalInvocationID.x;
for (int b = 0; b < 2; b++) {
    state[3] = uvec4(id*2 + b, N1, N2, N3);   // counter, nonce
    … 20 rounds, add input …
    uint base_block = id*32 + b*16;          // in 32-bit words
    for (int i = 0; i < 16; i++) {
        uint idx = base_block + i;
        if (idx >= data.length()) break;
        data[idx] ^= working[i/4][i%4];
    }
}

Encryption and decryption are the same operation, XOR with the keystream, so one shader handles both. The SSBO is read as little-endian 32-bit words, which matches the byte order ChaCha20 specifies when it serialises the keystream.

Host side

  1. Plan batches from image headers only (stbi_info) against a VRAM budget the user enters.
  2. Decode one batch into a contiguous buffer, record each image's offset and size, and pad it.
  3. Generate a fresh 32-byte key and 12-byte nonce with OpenSSL RAND_bytes.
  4. glBufferData → glDispatchCompute → glMemoryBarrier(GL_SHADER_STORAGE_BARRIER_BIT) → glMapBuffer.
  5. Write [count][metadata][ciphertext] to a .cb file, and the key and nonce to a separate file.

A new key and nonce per batch matters. The counter restarts at 0 for each batch, and reusing a key and nonce pair across two batches would reuse keystream. A 32-bit counter allows 232 × 64 bytes (256 GiB) per batch, far more than any VRAM budget.

Problems found on re-reading

1. Dispatch size (performance)

glDispatchCompute(ceil(paddedBytes / 256.0), 1, 1);   // local_size_x = 256

This launches about one invocation per byte. Each invocation covers 128 bytes, so only 1 in 128 invocations has data to touch. The rest run 40 rounds of ChaCha20 for blocks past the end of the buffer before the bounds check discards them. The correct count is ceil(paddedBytes / 128 / 256) work groups. No timing code exists in the project, so the size of this effect has not been measured.

2. Unsigned uniforms set with a signed call (correctness)

The shader declares uniform uint C1 … K8, N1 … N3. The host sets them through a helper that calls glUniform1i. The glUniform reference is explicit: using a signed-integer variant on an unsigned int uniform generates GL_INVALID_OPERATION, and the uniform keeps its previous value, which is 0. The code never calls glGetError. On a conforming driver, every batch would then be encrypted with an all-zero key, nonce and constant block, whatever RAND_bytes produced. Decryption would still "work", because it hits the same error. Some drivers are lenient, and this has not been tested on the original hardware.

The fix is glUniform1ui (or the 16 state words in a small uniform or storage buffer), plus a known-answer test: run the shader on the RFC 8439 block-function test vector and compare. That test would have caught this, and any future regression.

3. No integrity

ChaCha20 alone gives confidentiality, not integrity: flipping a ciphertext bit flips the same plaintext bit. A real file format would add Poly1305 (ChaCha20-Poly1305, as in RFC 8439) and authenticate the metadata header as well.

Summary

The data-parallel part, keystream blocks to invocations and SSBO in place, is straightforward and matches the cipher well. The problems are at the edges: how many threads to launch, how values reach the shader, and what the file format promises. The first two are one-line fixes. Neither would have survived a test against published vectors.
