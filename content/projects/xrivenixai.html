Overview

An Android app that runs large language models on the phone's CPU. There is no account, no backend and no cloud inference. Conversations and a long-term memory about the user are stored in a local SQLite database that is separate from the model, so switching or deleting a model keeps what the assistant remembers. The network is used only to download a model, after an explicit confirmation. The app label and APK are named "XrvinexAI".

Architecture

  • Native layer (app/src/main/cpp/pocketai.cpp). A JNI bridge to llama.cpp, which is a git submodule built with the NDK and CMake for arm64-v8a. It loads GGUF models, runs streaming generation on a main context, and runs grammar-constrained completion and embeddings on an auxiliary context. Between turns it trims the KV cache with llama_memory_seq_rm, so a follow-up message processes only its new tokens.
  • Kotlin layers. chat/ (turn orchestration, layered system prompt); knowledge/ (query routing, hybrid retrieval, memory extraction and validation); model/ (catalog, device-suitability rating, resumable downloads with SHA-256 checks); device/ (RAM, storage and CPU-feature profiling).
  • Storage. A Room database with migrations 1→4. Messages, memories and entities have FTS5 virtual tables (porter unicode61 tokenizer).
  • UI. Jetpack Compose with Material 3: Chat, Models, Memory and Settings screens, Markdown and LaTeX rendering, and streaming with a stop button.

Implementation: the memory path

  1. A router decides whether a message needs memories, older conversation or a date range. Small talk and general questions need none.
  2. Retrieval merges vector similarity (a bundled bge-small embedding model), FTS5 full-text matches and entity links into one score. Only memories above a per-route threshold are added to the prompt, at most six.
  3. After the reply, candidate memories come from both fixed rules and the model. Code then validates them: a candidate must be grounded in what the user said, duplicates are removed, and a new fact in the same topic slot (for example, where the user lives) replaces the old one, which is kept as history.

Model loading, generation and extraction share one serialised native dispatcher, so only one chat model is ever in memory.

Results / Validation

Measured on a OnePlus Nord CE 3 5G (Snapdragon 782G, 8 GB) with Qwen 2.5 3B Instruct Q4_K_M on 4 threads:

  • Model load about 10–12 s; resident memory about 3.2 GB after load.
  • Prompt processing about 15–20 tokens/s; generation about 5–6 tokens/s sustained over 5 × 128 tokens.
  • Time to first token about 1.8 s for a follow-up message with KV-cache reuse, against about 7 s without.

The repository has 30 JVM unit-test methods (memory logic, suitability rating, math normalisation) and 29 instrumented test and benchmark methods (retrieval, migrations, model switching, a performance benchmark). Three of the twelve catalog models were tested on a device.

Limitations

  • CPU inference only. A thread sweep found 3 threads faster than the default 4; the default has not been changed yet.
  • Android's default backup rules are left on, so app data can be included in a Google device backup if the user has that enabled.
  • Distributed as an APK on GitHub, not through an app store.
