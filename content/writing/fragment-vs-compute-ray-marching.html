I wrote the same kind of SDF ray marcher twice in OpenGL: once as a fragment shader on a full-screen quad, and once as a compute shader writing into a texture. The distance functions and the marching loop are nearly identical. What changes is how pixels map to GPU invocations, where the result lives and how it gets to the screen. This note compares the two repositories as they are, including the bug that broke the compute version's animation.

Fragment-shader version

The CPU draws two triangles covering the viewport. The rasteriser runs one fragment invocation per covered pixel, and the shader builds a ray from gl_FragCoord:

float x = -(float(gl_FragCoord.x)*2.0-1000)/1000;
float y = -(float(gl_FragCoord.y)*2.0-1000)/1000;
vec4 dir = normalize(x*camera.xAxis + y*camera.yAxis + camera.dir);

It marches at most 56 steps against map_the_world(), which returns the distance and an object id, and writes FragColor. Since the output is an ordinary colour attachment, adding post-processing only needs an FBO: pass 1 renders into a texture, and pass 2 runs a Sobel kernel over it.

The constant 1000 is the main flaw. Pixel coordinates are normalised by a hardcoded size, not the viewport, so the image stretches when the window is not 1000 px and the aspect ratio is wrong.

Compute-shader version

There is no rasterisation. The shader declares a work-group size and an image to write into:

layout(local_size_x = 10, local_size_y = 10) in;
layout(rgba32f, binding = 0) uniform image2D imgOutput;
…
ivec2 p = ivec2(gl_GlobalInvocationID.xy);
ivec2 dims = imageSize(imgOutput);
float x = -(float(p.x)*2.0 - dims.x) / float(dims.x);
…
imageStore(imgOutput, p, vec4(color, 1.0));

The host binds an RGBA32F texture with glBindImageTexture, dispatches (W/10, H/10, 1) groups, places a memory barrier, and draws a full-screen quad that samples the texture. Normalising by imageSize() makes this version independent of resolution, which the fragment version is not.

Two details are easy to get wrong here:

  • Dispatch rounding. W/10 is integer division. If the texture width is not a multiple of 10, the last columns are never written. Rounding up with (W + 9) / 10, plus a bounds check in the shader, covers every pixel.
  • Barrier bit. The code uses GL_SHADER_IMAGE_ACCESS_BARRIER_BIT, which orders later image load/store accesses. The display pass reads the result with texture(), and for sampler reads the specification asks for GL_TEXTURE_FETCH_BARRIER_BIT. Many drivers render correctly either way, but the second bit is the one that is specified.

Why the compute version stuttered

The compute repository's README notes a "weird stuttery behaviour" whenever objects are animated, and a text file of frame times shows an attempt to find it in timing. Re-reading the code for this note, the likely cause is in the uniform helper, not in the GPU:

void setFloat(const std::string& name, int value) const
{
    glUniform1f(glGetUniformLocation(ID, name.c_str()), value);
}

The parameter is an int. Every call such as compute.setFloat("angle", glfwGetTime()) truncates the time to whole seconds, so the animation advances in one-unit jumps instead of smoothly. The displacement parameter is also driven by 5 * tan(time), which runs off to infinity every π seconds. The fragment version's Shader::setFloat takes a float, which is why it animates smoothly. This has not been fixed and re-run yet, so it is a diagnosis from the source, not a confirmed result.

Which one to use

  • Fragment shader: the simplest path for one ray per pixel. Blending, MSAA and FBO chains come for free.
  • Compute shader: explicit control over the work-group shape, the output format and when the result is visible. It also opens the way to work the rasteriser cannot express, such as tile-based culling with shared memory, multiple passes over the same image, or writing to buffers. Neither repository uses those yet.

Neither repository measures frame time per frame. The compute version already wraps its dispatch in a GL_TIME_ELAPSED query but reads only the last result, at exit. Reading that query every frame in both versions at the same resolution is the comparison still missing.
