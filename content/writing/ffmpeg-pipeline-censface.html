censface-cpp reads a video, changes pixels inside some boxes, and writes a video that should otherwise match the input: same timing, same audio, same orientation. With the FFmpeg C API, that takes a chain of eight steps. This note follows one MP4 through them and records the places where the obvious approach fails.

Packets are not frames

av_read_frame() returns packets: compressed data for one stream, with pts/dts in that stream's time base. Video packets go to the decoder through the send/receive pair:

avcodec_send_packet(decoder, packet);
while (avcodec_receive_frame(decoder, frame) == 0)
    processFrame(frame);

One packet can produce no frame, because H.264 and HEVC reorder frames and the decoder holds some back, or it can produce several. AVERROR(EAGAIN) from receive_frame means "send more input". It is not an error. The encoder has the same shape (avcodec_send_frame / avcodec_receive_packet), and libx264's lookahead means packets come out well after the frames that produced them.

At end of file, both sides must be drained. Sending a null packet to the decoder and a null frame to the encoder makes them release what they are holding. Skip this and the last frames of the clip are missing.

Why convert pixel formats twice

Decoders output planar YUV, usually 4:2:0: a full-size luma plane and two quarter-size chroma planes. OpenCV's detector and effects want packed 8-bit BGR. So each frame is converted once with sws_scale into the cv::Mat's buffer, and once back to yuv420p for libx264.

The conversion needs the right YUV matrix and range. If sws_setColorspaceDetails is not called, swscale assumes BT.601 limited range, and full-range phone video shifts in colour. The deprecated yuvj420p format is mapped to yuv420p, and its implied full range is passed explicitly. The return conversion uses the same matrix, and the output stream is tagged with it, so the file is self-consistent.

One test clip had an MP4 colr box saying BT.709 limited while its HEVC bitstream said BT.601 full. The decoder reports the bitstream values, and censface follows the decoder, as the ffmpeg CLI does.

Rotation is metadata

Phones store portrait video as landscape pixels, plus a display matrix in the stream side data (AV_PKT_DATA_DISPLAYMATRIX). A player rotates at display time. A detector run on the raw frame sees people lying sideways. censface reads the angle with av_display_rotation_get, rotates the cv::Mat with cv::rotate, swaps the encoder's width and height for 90° and 270°, and writes no rotation tag. Players then do not rotate the already upright frames a second time.

Keeping timestamps

The common way to set up an encoder is a fixed frame rate with a time base of 1/fps. That quietly retimes variable-frame-rate phone clips. censface sets the encoder's time_base to the input stream's time base and gives each output frame the source frame's best_effort_timestamp and duration. With AV_CODEC_FLAG_FRAME_DURATION, libx264 carries each duration through to its packet.

The muxer may still choose its own time base in avformat_write_header. So every encoded packet goes through av_packet_rescale_ts(packet, encoder->time_base, stream->time_base) before av_interleaved_write_frame. Frames whose timestamp does not increase are dropped and counted, because the encoder rejects them.

Audio without decoding

Audio is never decoded. For each input audio stream, avformat_query_codec asks whether MP4 can store the codec. If it can, an output stream is created with avcodec_parameters_copy and codec_tag = 0, so the MP4 muxer picks its own tag. Audio packets are then copied byte for byte, with only their timestamps rescaled. av_interleaved_write_frame buffers enough to write audio and video in timestamp order, even though audio packets arrive long before the encoder releases the matching video. Since both streams keep their source timestamps, A/V sync is preserved.

Cleanup on every path

Each FFmpeg object (format contexts, codec contexts, SwsContext, frames, packets) sits in a std::unique_ptr with a deleter that calls the matching free function. Every error code goes through a check() that throws with FFmpeg's error text. When anything fails, or when Ctrl+C sets the cancel flag, the destructors release everything in reverse order. main() then deletes the hidden .name.partial.mp4 file, so a half-written output never sits under the real file name.

What was checked

Recorded in the repository README, run by hand on one machine: a 2 s H.264 and AAC clip kept 24 of 24 frame timestamps and byte-identical audio (MD5). A rotated variable-frame-rate clip kept its duration and came out upright with no rotation tag. Peak memory was 486 MB for 6 s of a 720p HEVC clip and 490 MB for all 29 s. Speed was not measured.
