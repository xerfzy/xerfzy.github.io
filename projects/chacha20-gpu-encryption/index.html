ChaCha20 GPU Image Encryption

Batch image encryption with ChaCha20 in an OpenGL 4.3 compute shader. Images are packed into one SSBO per VRAM-sized batch and XORed with a GPU-generated keystream.

Overview

A desktop tool that encrypts whole folders of images with the ChaCha20 stream cipher, doing the cipher work in an OpenGL 4.3 compute shader. Images are decoded, packed into one contiguous buffer per batch, uploaded as a Shader Storage Buffer Object (SSBO), encrypted in place on the GPU and read back into a single .cb file per batch. Decryption runs the same shader with the same key and nonce, because XOR with the keystream is its own inverse.

Problem / Motivation

ChaCha20 is built from 32-bit add, rotate and XOR operations, and each 64-byte keystream block depends only on the key, nonce and a block counter. Blocks can therefore be computed independently, which suits a GPU. The project tests that mapping on real image batches, with the CPU doing only file I/O and buffer packing.

Implementation

  • Shader (shaders/chacha_compute.ps, GLSL 4.30). local_size_x = 256; the state constants, key and nonce are passed as uniforms. The quarter-round uses rotations of 16, 12, 8 and 7, followed by 10 double rounds (column, then diagonal) and the feed-forward addition. Each invocation produces two consecutive 64-byte blocks (counter id*2 + b) and XORs 32 words of the SSBO in place, with a bounds check at the end of the buffer.
  • Batching. The user enters the GPU's VRAM in megabytes. stbi_info reads only image headers to get width × height × channels, and files are grouped into index windows that fit the budget before anything is decoded.
  • Packing. Each batch is decoded with stb_image into one std::vector<uint8_t>, padded to a 128-byte boundary. Per-image metadata (height, width, channels, size, byte offset) is kept for reconstruction.
  • GPU round trip. glBufferData(GL_SHADER_STORAGE_BUFFER, …), glDispatchCompute, glMemoryBarrier(GL_SHADER_STORAGE_BARRIER_BIT), then glMapBuffer to read the ciphertext back.
  • Keys. Each batch gets a fresh 256-bit key and 96-bit nonce from OpenSSL RAND_bytes, saved next to the output as N_key.bin.
  • File format. [image_count][metadata array][padded ciphertext].
  • UI. Dear ImGui windows for encrypt, decrypt and logs, with a native folder picker. Source images are never modified.

Technical decisions

  • Packing every image into one SSBO means one upload, one dispatch and one readback per batch, instead of one per image.
  • Planning batches from headers keeps host memory bounded by the VRAM budget, not by the dataset size.
  • Builds with CMake on Linux (OpenGL, GLFW, OpenSSL) and with a Visual Studio project on Windows.

Challenges / Limitations

  • Uniform types (open issue). The shader declares the constants, key and nonce as uint uniforms, but the host sets them with glUniform1i. The OpenGL specification treats that as GL_INVALID_OPERATION and leaves the uniform unchanged, so on a strict driver the keystream would not depend on the key, even though round trips still succeed. The fix is to upload with glUniform1ui and add a known-answer test against the RFC 8439 test vectors.
  • Dispatch size. The host dispatches ceil(bytes / 256) work groups of 256 invocations, about one invocation per byte. Each invocation covers 128 bytes, so most invocations compute blocks past the end of the buffer and discard them. Dispatching ceil(bytes / 128 / 256) groups would remove that work. This is the next change.
  • No authentication. ChaCha20 alone gives confidentiality, not integrity. There is no MAC (for example Poly1305), so tampering with a .cb file is not detected.
  • Key files are written in plain form next to the output. Protecting them is left to the user.
  • The repository also contains build outputs and Windows libraries.

Results / Validation

Encrypted batches decrypt back to the original pixels through the same shader. Decryption writes each image as PNG with stbi_write_png, so the original file encoding (for example JPEG) and metadata are not kept.

On an RTX 3050 (6 GB) throughput was roughly 200–500 MB/s. There is no timing instrumentation in the code yet, so this is an observed range, not a benchmark.
